# التشغيل والتحقق والتراجع

نفّذ من نسخة معزولة وباعتمادات المشروع المثبتة؛ لا تستخدم قاعدة عملاء في الاختبارات. لا تضع سرًا في وسيطة أمر أو ملف تقرير. الاتصال المصرح يحقن عبر مدير الأسرار.

## فحوص المراجعة

```bash
cd frontend
npm ci
npm run typecheck
npm run lint
npm test
npm run build
```

من جذر المشروع:

```bash
python scripts/audit/protected_manifest.py
python -m pytest tests/unit/audit tests/unit/auth/test_session_revocation_guards.py -q
python scripts/audit/run_with_local_redis.py --redis-server /path/to/redis-server -- tests/unit/auth tests/unit/subscriptions tests/integration/api/test_auth_routes.py tests/integration/api/test_admin_rbac_coverage.py tests/integration/api/test_admin_routes.py tests/integration/api/test_auth_rate_limiting_identity_isolation.py tests/integration/api/test_portfolio_subscription_gating.py tests/integration/api/test_market_data_subscription_gating.py tests/integration/api/test_watchlist_route.py tests/integration/api/test_notifications_route.py tests/integration/api/test_subscriptions_routes.py -q
```

مشغل Redis يرفض منفذًا مستخدمًا ولا يوقف خدمة أخرى؛ ينشئ خدمة محلية مؤقتة دون حفظ ويغلقها بعد الاختبار. آخر تشغيل موسع سجل 319 نجاحًا؛ أوامر إعادة التحقق يجب أن تعمل على نفس SHA والتبعيات للحصول على مقارنة عادلة.

التقرير اليدوي، بعد حقن `BASIRAH_AUDIT_DATABASE_URL` لحساب **قراءة فقط**:

```bash
python scripts/audit/daily_evidence_report.py --day 2026-09-09 --output /approved/reports/2026-09-09-observation-01.json
```

المجلد موجود مسبقًا، واسم الملاحظة جديد دائمًا. لا يطبع الاتصال عند الفشل. لا يُحسب نجاح التشغيل نجاحًا لجودة السوق: افحص missing_quote_timestamp وreal_data_not_confirmed وactionable_without_outcome وآخر فحص؛ الحقول المفقودة تتطلب تحقيقًا، لا صفراً مستنتجًا للربح.

## الدفعات والنشر

1. مراجعة فرق الواجهة، ثم فرق الحسابات، ثم أدوات/وثائق التدقيق في commits منفصلة.
2. تشغيل CI كامل بالتبعيات المثبتة وPostgreSQL، والتحقق من الترحيلات القائمة؛ لا ترحيل جديد لهذه الدفعة. CI الخلفية الحالي يعمل لطلبات main؛ الطلب المتراكم فوق PR114 يحتاج تشغيلًا مناسبًا ولا يعني غياب فحصه نجاحه.
3. مراجعة مستقلة للاستهلاك المشروط والتعامل مع فشل Redis/DB، واختبار طلبَي refresh متزامنين في PostgreSQL، وتجربة رموز قديمة وجديدة.
4. لا تطبق 56 تغييرًا معلقًا في Railway دفعة واحدة. قارن كل تغيير وأثره ومصدره، واستخدم نشرًا تجريبيًا محدد النسخة بعد عزل التغييرات المطلوبة.
5. رحلتان بجلستين تجريبيتين منفصلتين، عبر إدخال دخول آمن: مدير ثم مستخدم جديد. البريد والتحقق والاستعادة وخروج كل الأجهزة، محاولة API إدارة بحساب عادي، معرف مستخدم آخر، تعليق حساب وانتهاء استحقاق. Safari فعلي وChrome/سطح مكتب وجوال. لا تستخدم صور المستخدم بديلًا لإعادة الاختبار.
6. بوابة بيانات فعلية أثناء السوق بمصدر مرخص، ثم متابعة قياس أمامية. لا تغيير سلوك Brain/Shadow/Recurrent Scan أو التقويم المؤثر دون أثر وموافقة.
7. لا نشر إنتاجيًا ولا باقات مدفوعة قبل موافقة المستخدم؛ هذه الدفعة لا تطلب شراء خدمات ولا تغير صلاحيات العملاء.

## التراجع

لا تغييرات schema؛ يمكن التراجع عن دفعة الواجهة وحدها. لحزمة الحسابات يُفضّل إصلاح لاحق أو revert كامل للدفعة بدل انتقاء ملف JWT وحده. رمز sid متوافق مع مفكك JWT السابق لكن العودة للكود القديم تعيد قيد الإبطال الفردي القديم؛ لذلك راجع الحاجة لإبطال شامل مصرح قبل التراجع الأمني. لا تمسح جلسات أو بيانات للتسهيل دون اعتماد.

احتفظ بـ SHA المرجع والنسخة المنشورة ومراجعة متغيرات البيئة **دون قيم الأسرار**. جرّب إعادة نشر النسخة السابقة في بيئة معزولة قبل الإنتاج؛ لم يُنفذ نشر/تراجع حي في هذه المهمة. النسخ الاحتياطي لا يُعد مثبتًا حتى تستعاد نسخة في DB جديدة ويُتحقق من العد والعلاقات والاستعلامات والصلاحيات؛ هذا لم يُختبر هنا.

## المتابعة المطلوبة لإغلاق العوائق

الوصول الآمن لبيئة اختبار تحوي بيانات مصرحًا بها، حسابا اختبار، بريد اختبار قابل للتحقق، نسخة PostgreSQL معزولة، وCI مطابق. يلزم مرور جلسات وأفق انتهاء توصيات فعلي للحصول على النتائج؛ لا موعد يثبت جودة قبل اكتمال العينة. تثبيت قواعد القياس والحد الأدنى المناسب للعينة وتوزيع الظروف سابق لتحليل الأفضلية. لا متابعة مستقبلية مزعومة ولا عائد مضمون.
